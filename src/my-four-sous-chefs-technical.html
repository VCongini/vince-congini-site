Private-repo case study

A production AI app, built past the demo line.

My Four Sous Chefs turns pantry, fridge, and shopping-list context into practical dinner decisions. The source is private, so this walkthrough shows the architecture, product surfaces, and production controls that matter when an AI feature becomes a real SaaS application.

Product Story

This project is strongest when the visitor can see both sides at once: a family-facing food product and the engineering discipline underneath it. The page now leaves clear room for more app screens as the product story grows.

How It Works

01

Capture messy kitchen context

Users can bring photos, pantry lists, shopping-list context, and preferences. The interface stays oriented around dinner decisions, not prompt writing.

02

Turn inputs into structured product state

Image preprocessing, OCR, vision-assisted extraction, structured parsing, and normalization convert imperfect inputs into ingredients the rest of the product can trust.

03

Generate useful recipes, not novelty output

AI calls are isolated behind API boundaries with typed responses, fallback handling, token-budget awareness, and UI states for slow or partial results.

04

Persist the value after generation

Saved recipes, meal plans, usage records, account state, and entitlements make the app a continuing product rather than a one-off generation tool.

Architecture

TypeScript product system

My Four Sous Chefs is organized as a TypeScript monorepo: React and Vite for web, Expo and React Native for mobile, Express for the API, shared domain packages, and Supabase-backed persistence for user and product state.

The split keeps the product fast to iterate while protecting the boundaries that matter: AI calls, billing events, identity, quotas, and saved user data.

Production Controls

Cost

Meter before expensive work starts

Identity-aware limits, daily and monthly token budgets, request metering, and reservation-style accounting keep AI usage controlled before provider calls are made.

Abuse

Treat AI endpoints as protected resources

Cloudflare Turnstile, authenticated usage records, and quota-aware API paths reduce abuse without making the family-facing flow feel hostile.

Reliability

Design for partial success

Structured logging, observable request outcomes, rollback handling, and automated coverage around critical flows keep failures understandable and recoverable.

Engineering Decisions

Boundary

Keep AI work server-side

Provider keys, cost controls, prompt assembly, and structured parsing stay behind server boundaries. The client owns interaction quality; the API owns trust, metering, and external calls.

Data

Persist product state, not raw experimentation

Recipes, plans, account state, and usage records are first-class data. This makes the product useful after the first generation and gives production controls durable state to enforce.

Delivery

Favor boring deployable pieces

The architecture uses familiar TypeScript, web, database, and payment primitives. The interesting work sits in product judgment, AI workflow design, and reliability controls rather than novelty for its own sake.

What This Demonstrates

My Four Sous Chefs is a useful portfolio proof point because it combines modern front-end architecture with the parts that make AI products hard in production: unreliable inputs, variable model outputs, cost exposure, subscription state, operational feedback, and user trust.

The source is private, but the public architecture story shows the same thing a repository walkthrough would need to prove: clear boundaries, practical product thinking, and production discipline around an AI-heavy user experience.
